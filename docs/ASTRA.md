# GPT-6 Astra：功能開發與驗證指引

先讀 [共用須知](../AGENTS.md)。本檔是使用者指定的角色分工，不會自動選擇、啟動或切換模型。
若執行工具沒有自動讀取 AGENTS.md，請在任務開頭明確指定閱讀這兩份文件。

## 交付目標

開發可執行的新功能，釐清其效果與限制，讓 Claude Opus 5.5 能接續整合。
以既有程式為基礎，優先用函式、原有類別與 dict 狀態擴充；避免平行版本、猴子補丁與只為包裝資料而新增物件。
目前 `FrameProcessor`、`ModelPipeline` 已是明確責任邊界，不應重新拆回分散於主迴圈的臨時邏輯。

## 建議工作順序

1. **定位問題**：列出影片、秒數、原始與規則用車輛 ID、預期事件、目前診斷原因。
   ID 會因模型／追蹤設定變動，不能把舊輸出的 vehicle 編號當跨版本唯一真值。
2. **建立對照**：記錄 HEAD、dirty diff、模型設定、權重 SHA-256、影片範圍與已有測試。
   讀取資料前確認實體檔案仍在；缺少輸出或權重時誠實列出限制。
3. **決定責任位置**：模型問題放 `model_library`；逐幀資料組裝放 `frame_processing`；幾何放既有雙線／區域模組或共用工具；規則放規則模組；呈現放輸出模組。
4. **實作最小完整功能**：沿既有資料流接上設定、來源標記、規則、診斷與輸出；新的實驗性行為預設不影響既有流程。
5. **驗證反例**：除正例外，測試正常通過、短暫接觸後返回、低信心、遮擋、跳幀、換 ID、運動失效、影片結束等與本次改動相關情況。
6. **交付 Opus**：填寫 [交接範本](handoff/TEMPLATE.md)，附差異與可重現命令；共用介面需要改動時明列提案與讀取端遷移。

## 驗證的界線

- 單元測試驗證規則與契約，不能代替真實影片準確率。合成案例命中只證明流程可運作。
- 只改規則時先使用已存 JSONL 重算；改區域／雙線後處理需要遮罩與原影片。已有 JSONL 的方框、像素數不足以還原完整語意遮罩。
- 模型更換與規則調參分開比較。維持影片、區間、預處理、裝置和評估方式一致，並報告變差案例。
- 區域存在、車框存在、事件數增加，皆不等於準確率提升。接地梯形是估計；50% 是該近似多邊形的重疊比例。
- 未 `reviewed` 的影片不可當完整負例；不要依系統輸出自動把 ground truth 改成有利答案。
- 從前後幀推估的標線與燈號延續必須保留來源；不能將估計偽裝成新觀測來湊足時間證據。
- 量測推論頻率時要看事件時間、狀態、漏判與誤報，不只看 FPS。不要同時執行其他 GPU 實驗。

## 與 Opus 協作

- 功能分支應能獨立執行相關測試與最小驗證，不把「接上主流程」全部留給整合方。
- 可在不破壞讀取端的前提下提出向後相容欄位；需改共用簽名或既有欄位語意時，先把生產端／消費端與遷移方案寫入交接。
- 避免為方便單一功能重寫模型工廠、觀測 schema 或事件輸出；讓 Opus 統整共用邊界。
- Opus 調整架構後，依交接中的案例核對行為；若確認條件或輸出變了，視為新的行為變更再驗證。

## 新權重交付給系統時

要求訓練端提供模型架構／大小、部署檔、SHA-256、類別順序、輸入尺寸與正規化、輸出格式、匯出工具版本及獨立驗證結果。
OCR 需確認推論模型資料夾與字典；ONNX 需確認輸入形狀、動態維度與後處理。單換檔名不代表架構相容。
同架構微調優先只換設定與權重；跨版本升級必要的轉換限制在模型後端，並驗證原圖座標與追蹤介面。
保留可取得的舊權重與設定，不能以 git 回退程式取代未納入 git 的模型檔回退。
